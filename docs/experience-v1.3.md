# Training Data Market v1.3 — 参加者の手応えを返すUX

## なぜ変更するか

v1.2 は投票、確率予測、時間制バッチ学習を実行できるが、**選択画像が投票枠から採用されたか本人が確認できない**。現在のゲーム進行でも、前回の結果で現在の「04 結果」が完了扱いになる。24時間制のゲームでは、この2点が参加継続の妨げになる。

## 1ラウンドの体験

1. **最初の行動を明示**：ページの「YOUR NEXT MOVE」から、未推薦なら画像探索、推薦済み・未予測なら確率予測、提出済みなら締切と過去結果を確認する。
2. **提出状態を保持**：推薦と勝敗予測は別々に即時保存。ボタンは相手のデータを直接学習させるものではない。
3. **時間制バッチ**：投票の締切、凍結、2アーム学習、公開の順。画面はサーバー状態を唯一の情報源にする。
4. **公開後の個人フィードバック**：公開済みラウンドの本人だけに、推薦枚数と投票枠採用枚数を表示。予測ポイントは既存のスコア欄に表示。勝敗と共有AIへの採用は別の判定。
5. **次のクエスト**：「直近の公開結果」と「現在の投票」を別ラウンドとして説明。前回が公開されても現在のラウンド進捗を勝手に完了にしない。

## データ契約

- `GET /v1/rounds/{round_id}/participation/me`：匿名署名セッション本人の `recommended_ids`, `recommended_count`, `adopted_ids`, `adopted_count`, `status` を返す。
- `adopted_ids` は厳密に `本人推薦 ∩ 結果JSONの voted_ids`。`selected_ids` はランダム補完を含むため採用判定に使わない。
- 結果JSONの `voted_ids` はCommunityバッチのうち票に基づき採用されたIDのみ。公開前は採用枚数は `null`。
- 旧ラウンドなど `voted_ids` が欠ける場合は `adopted_count:null`。「0枚採用」と推測しない。
- 個別データの因果効果は主張しない。`promotion==='random'` または `rollback` でもCommunityアームへの投票枠採用実績は表示するが、共有モデルに反映したとは言わない。

## UX受入条件

- フォーカス可能な「次の行動」ボタンが状態別に正しい場所へ移動する。
- 前回ラウンドの結果は `round_id` を表示し、現在ラウンドと区別する。
- 同一ブラウザの署名セッションだけが本人の採用結果を読め、別セッションでは別の結果となる。
- 結果APIが成功し、本人結果APIが失敗した場合、公開結果を消さない。
- 旧ラウンド、未投稿、採用0件、モデル更新不採用のすべての状態で誤認を生まない。
- 390px幅と1440px幅で横方向のはみ出しがない。ゲーム専用CSSもブラウザ検査に含める。
- スマートフォンでは結果・説明画面の閲覧中に推薦用の固定ボタンで内容を覆わない。

## 計測計画（未実施）

初見参加者5〜10名を対象に、①推薦までの到達率、②予測までの到達率、③締切・学習実行の理解、④結果と個人採用の意味の理解を観測する。目標は初回推薦完了率80%以上、個人フィードバック理解率80%以上。これらは目標値であり測定結果ではない。公式CIFAR-10の実測性能とSites本番公開は別途検証する。
