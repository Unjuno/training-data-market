# Training Data Market — UX品質仕様・検証記録 v0.7

**対象:** CIFAR-10画像選択ゲームの静的デモとライブUI。
**状態:** ユーザビリティ上の欠陥修正とローカルChromiumの合成API E2Eを実施。実サービスのユーザーテストやSites配信確認は未実施。

## 1. 最優先のユーザージャーニー

1. モデルのクエストとモード（実測LIVE／模擬DEMO／未初期化）を判別する。
2. 画像ID・クラス・誤分類から学習候補を探す。
3. カードの「推薦する」操作を行い、推薦の保存可否を確認する。**クリック後にモデルが即学習するという誤解を与えない。**
4. 最大10件の推薦リストを確認・取り消しできる。推薦理由の**メモ保存とは別操作**であることを理解できる。
5. 締切後の学習・検証結果をCommunity対Randomで比較する。過去の結果を実験として示し、個人画像の因果効果を断定しない。

## 3. 主要な設計判断

- ライブUIの「推薦」は**API保存操作**。推薦理由入力のボタンは**メモの保存**に限定した。ユーザーが二度「投票確定」を押す必要はない。
- デモも画像推薦をローカルストレージへ直ちに保存し、ライブとの違いを減らした。ローカルストレージ利用不可の場合は明示する。
- 未保存メモを入力中、推薦追加・削除でデータ再取得しても入力内容を破棄しない。
- APIは48件最大ページングに対応するが、モバイルでは12件としてスクロール負荷を減らす。PCとスマホの表示枚数を意図的に変える。
- 長い画像一覧の最下部にもページ移動操作を配置し、次ページへ移ると探索エリアに戻す。
- サーバー未初期化・画像一覧失敗・検索結果0件は異なる状態として扱う。
- システムメッセージは色だけに依存させず、文章、aria-live、操作ボタンで支える。

## 4. ローカル検証

`npm run check`、`npm run build`、`python -m pytest tests_py -q`、`python tests_e2e/ux_flow.py`。

任意のChromium UX検査は `playwright` とローカルのChromiumを必要とする。E2Eは**合成API**を用いるため、実際のSites、CIFAR-10精度、投票ユーザー数、永続性を測定した結果ではない。

確認したシナリオ：自動検索、推薦後のキーボードフォーカス、サーバー保存確認、同ラウンドでの投票再取得、編集中メモの保護、保存失敗時の画像ID維持、通信失敗と空結果の区別、再試行、下部ページング、390px表示の横はみ出し、モバイル最大12件の取得。

## 5. 次に必要な人間によるユーザビリティ試験

**H — 反証可能な仮説:** 初めて画面を開く人の80%以上が、実測・模擬の区別を理解し、2分以内に画像1枚を適切に推薦できる。推薦が即座に再学習を起こすと誤認する参加者の割合は5%以下を目標とする。

**T — 最小検証:** 製品の予備試験で初見利用者10人以上を観察し、行動ログではなく説明の発話とタスク達成を記録する。フィードバック後、事前登録した手順で20人以上を固定人数で再試験する。PC/スマホ、初心者/機械学習経験者を分けて記録する。

**D — 判定:** この研究では、上記2条件をともに満たせば暫定PASS、いずれか未達なら改善対象、標本数や評価が不足すればUNCERTAIN。推測統計的な一般化を保証する基準ではない。

**C — 破れ方:** 抽象サムネイルではデータの内容が見えない、専門用語で判断が止まる、推薦が自動保存されたと理解できない、スマホで長い一覧を移動できない、同じユーザーの再学習効果を誤認する。

**U — 不確かさ:** 初心者割合、端末サイズ、通信速度、CIFAR-10画像公開可否、学習開始状態、試験参加者の自己選択バイアス。信頼区間や合成標準不確かさは実測前のため算定不能。

## 6. 公開に向けた未解決事項

実CIFAR-10画像が権利確認されるまで代替アートしか見えないため、ゲーム本来の「画像を見て有効なデータを探す」体験はまだ評価できない。Sites上では認証・共有投票・API接続・バックグラウンド学習の完走が必要。公開後はLighthouse／axeなどのアクセシビリティ確認、低速回線・弱視・キーボード単独・スクリーンリーダーの試験を別途実施する。

関連領域：HCI（操作エラーの予防）、認知心理学（メンタルモデルとフィードバック）、機械学習（損失表示の統計的解釈）、ゲームデザイン（行動と報酬の対応）。
